# Мост к провайдеру модели для ACP и упрощение шлюза

Статус: принято для GigaLoom 0.9.1 4 августа 2026 года.

## Контекст

ACP stdio соединяет GigaLoom с процессом агента. Сам агент обращается к
провайдеру модели по отдельному HTTP-протоколу. Поэтому поддержка ACP не
означает, что агент умеет работать с OpenAI-совместимым endpoint, другим
базовым URL или произвольным псевдонимом модели.

В GigaLoom 0.9.0 эти факты трактуются двумя несовместимыми способами. Обнаружение
маршрутов правильно связывает OpenAI Chat Completions с ACP-потребителем, но
общий механизм настройки распознаёт ACP только тогда, когда сам протокол
маршрута называется `acp`. Управляемый ACP-путь обходит этот механизм и хранит
отдельную таблицу возможностей только для OpenCode. Расширение любого из этих
путей сохранило бы неоднозначность и дублирование данных о маршрутах и
провайдерах.

## Решение

### Где находится мост

Настройка провайдера модели становится частью существующего жизненного цикла
управляемого ACP-запуска. GigaLoom не добавляет отдельный ACP proxy daemon. Такой
процесс должен был бы повторить работу с сессиями ACP, отменой, разрешениями,
потоковыми ответами, MCP, аутентификацией и жизненным циклом процессов, но всё
равно не смог бы заставить агент принять неподдерживаемый endpoint провайдера.

Последовательностью запуска по-прежнему владеет GigaLoom:

1. разрешить один актуальный маршрут шлюза;
2. подготовить изолированное окружение процесса;
3. запустить и инициализировать ACP-агента;
4. применить проверенную стратегию настройки провайдера;
5. создать ACP-сессию и выбрать модель;
6. выполнить запрос и очистить принадлежащее GigaLoom состояние процесса.

Ни одна стратегия не изменяет нативный каталог агента.

### Транспорт и протокол провайдера разделены

План маршрута хранит эти измерения отдельно:

- `transport_kind` — способ связи GigaLoom с агентом, например
  `acp_stdio_v1`;
- `provider_protocol` — способ связи агента с выбранным шлюзом, например
  `openai_chat_completions` или `openai_responses`.

ACP-потребитель должен принимать маршрут, в котором провайдер использует OpenAI
Chat Completions. Он не должен требовать, чтобы протокол провайдера назывался
`acp`.

### Один разрешённый маршрут

Один внутренний неизменяемый `ResolvedGatewayRoute` хранит идентификаторы
маршрута и шлюза, протокол провайдера, URL без учётных данных, публичный
псевдоним модели, статус поддержки, digest возможностей и идентификаторы
причин. Учётные данные передаются отдельной runtime-зависимостью.

Один resolver создаёт этот объект или типизированный отказ для нативного
запуска, управляемого ACP, CLI dry-run и Web preflight. Пользовательские
интерфейсы не интерпретируют ответы со списком моделей и возможностями
самостоятельно. Существующие внешние JSON-контракты остаются стабильными до
обычной версионированной миграции.

### Сначала проверяются возможности

Стратегии настройки провайдера применяются в таком порядке:

1. методы ACP `providers/*`, объявленные во время `initialize`;
2. встроенный адаптер, точно совпавший по registry id и ограниченной политике
   версий;
3. явный результат «только нативный провайдер».

Встроенные стратегии — методы провайдера ACP, проверенные переменные окружения
OpenAI и проверенная временная конфигурация. Отсутствие поддержки — результат
разрешения, а не четвёртая стратегия. Неизвестные агенты не получают
автоматический fallback через переменные OpenAI.

Если агент объявляет методы провайдера, но проверка list, set или повторного
чтения не проходит, запуск блокируется. GigaLoom не переключается незаметно на
адаптер, потому что это скрыло бы регрессию контракта. Выбор модели шлюза для
агента, который поддерживает только нативного провайдера, также блокируется до
передачи сессии; обычный нативный запуск остаётся доступен.

### Владелец возможностей шлюза

Данными о провайдерах и моделях владеет gpt2giga. GigaLoom использует его
публичные контракты инспекции, `/models` и `/bridge/capabilities`, не определяет
возможности по именам моделей и не хранит второй каталог моделей.

Обычный управляемый запуск проверяет совместимый диапазон версий, публичные
ревизии машинных контрактов и наблюдаемые данные установленного артефакта.
Точный digest исходного артефакта не является единственным правилом
совместимости для известного пакетного шлюза. Для неизвестного executable
сохраняется более строгая проверка локального артефакта.

### Хранение и секреты

Onboarding может сохранить обезличенную проекцию возможностей моста в
существующей записи установки. В ней допустимы стратегия, поддерживаемые
протоколы, идентификатор и ревизия адаптера, способ выбора модели, статус и
идентификаторы причин. В ней не должно быть учётных данных, значений заголовков,
сгенерированной конфигурации, пользовательских путей, ответа провайдера или
запроса.

Маршрут запуска содержит только URL без учётных данных. Секреты разрешаются на
границе процесса или транспорта и не попадают в планы маршрутов, квитанции,
логи, диагностику или сохранённое состояние проверки.

## Граница упрощения

Новый мост заменяет управляемый путь только для OpenCode, а не работает рядом с
ним. После миграции:

- модуль управляемого шлюза только для OpenCode удалён;
- общий нативный механизм больше не создаёт отдельный ACP selector;
- остаются один resolver маршрута шлюза и один resolver ACP-моста;
- не добавляются daemon, постоянное хранилище и обязательная runtime-зависимость;
- для ACP-моста добавляется не более двух production-модулей;
- число production-строк в затронутых ACP- и gateway-путях не превышает
  зафиксированную базу 0.9.1.

Полная переработка CLI, сессий, frontend и evidence framework не входит в
patch-релиз.

## Миграция и откат

Старые onboarding-записи без данных о мосте остаются читаемыми и показывают,
что нужна повторная проверка. Probe или update заполняет добавочную проекцию,
не создавая сессию и не обращаясь к провайдеру модели.

Для отката достаточно не выбирать шлюз: агент использует нативного провайдера.
Временная конфигурация исчезает вместе с управляемым процессом или временным
каталогом. Пользовательскую конфигурацию восстанавливать не нужно, потому что
GigaLoom её не изменяет.

Если проверка совместимости по контрактам даёт регрессию, следует сузить
диапазон совместимых версий, сохранив наблюдаемые данные артефакта. Нельзя
возвращать жёстко заданный digest исходного кода как обычный механизм допуска
или добавлять второй resolver.

## Последствия

Поддержанные ACP-агенты используют маршруты шлюза без ручной нативной
конфигурации, а неподдержанные честно остаются в нативном режиме. У данных
маршрута один владелец, ошибки возможностей провайдера видны до сетевого вызова,
а запуск остаётся в существующих границах процессов и безопасности.
